## Engine draft orientation

engine.js is a new, small implementation, not a patched v0.3 engine. Do not assume it inherits v0.3 test coverage.

- Browser global: Ferryman. Node: require('./engine.js').
- Public API: version, NODES, TEMPLATES, MEMORIES, createGame(seed), dispatch(state, action), preview(state, to, memoryId), routes(state), soul(state,id), partner(state,id), seats(state), forecast(state), deliveryPreview(state,ids), validate(state), serialize(state), deserialize(text).
- dispatch clones the input, returning {ok,state,error}; rejected actions retain the original state.
- Persisted phases: boarding -> route -> memory -> review -> result. Destination results continue into delivery; delivery results continue to route. Shore returns continue into boarding. Failure results continue into ended.
- Actions: BOARD/UNBOARD with id; READY; ROUTE with to; MEMORY with id (or null) and optional target; BACK; RELEASE with wraith id; CROSS with confirm:true only when accepting a lethal crossing; DELIVER with ids; CONTINUE.
- Selecting a memory is provisional. CROSS consumes it and applies any waiting-soul protection. BACK should let the player revise choices before committing.
- State includes source-specific memories, hand/deck/discard, cohort IDs, waiting/separation/guard markers, visited stops, result text, and delivery/run totals.
- Save validation is handwritten and untested. Review it carefully before accepting imported saves.
- Text is English. Use textContent or equivalent safe DOM creation when rendering imported state, never interpolate save text as HTML.
- preview gives the complete fog breakdown and resulting light; use it for route/memory/review screens rather than duplicating rules in app.js.

## Paper-play considerations for the eventual v0.4 kit

Added at the user's request on September 29. These are design and usability considerations for the next implementer, not newly approved mechanics. The browser-first scope and paused build remain unchanged; do not generate the physical kit yet.

### Make the guided flow usable without a screen

Use a small stack of reusable instruction cards or a phase strip with a movable marker: passengers, route, memory, crossing result, delivery. Provide a separate return-to-shore checklist. Intermediate stops skip boarding. The reminder for drawing memories belongs after arrival/delivery resolution, not after playing a card.

Show the current instruction prominently, but keep the light track, occupied seats, waiting souls and their anger, active wraiths, and current/visited stops visible. "One thing at a time" should mean one decision at a time, not hiding facts needed to make that decision. This also applies to the browser design.

The review screen needs a physical equivalent: place the chosen route and optional memory in a pending area. The player may revise them before confirming departure. Commit the memory, its protection mark and crossing cost together; do not make Back require reconstructing a discarded card or an erased light total.

### Prefer component placement over a separate ledger

| State | Candidate physical representation |
|---|---|
| Lantern light | One shared numbered track and marker, showing the current 0-6 range |
| Boat capacity | Four printed seat spaces; a two-seat soul clearly occupies two spaces |
| Current/visited locations | One location marker and simple visited markers, reset on return |
| Waiting anger | A small track on each soul card, readable without a separate lookup |
| Separation and memory protection | Distinct temporary markers on the affected waiting card, with their expiry printed |
| Wraiths | Move the original soul card into a visible wraith area, preserving identity for release |
| Memory circulation | Clearly separated reserve, draw, hand, pending and discard areas |
| Cycle modifier/favored destination | One compact reminder beside the route reference, advanced only on return |

These are representations of existing state, not new resources. Avoid duplicating the same state on both cards and a mandatory ledger. New souls enter after anger resolves, so test whether the visible waiting area makes a separate departure-snapshot ledger unnecessary under the revised return rule. Do not remove separation/protection distinctions: normal-anger protection still does not cancel separation anger.

Remove the obol bank, hull/reprimand tracks, quota calendar, repair/rocky-route pieces and paid-calming reminders from the future v0.4 kit. Do not merely cross them out on the main player aid.

### Keep retained abilities practical to resolve by hand

The user kept the existing abilities. Print each soul's seat cost, wish, ability and matching-group identity where it can be read in the boat. Give linked partners and opposing soldiers a shared group marker so different cohorts cannot accidentally interact.

Provide one crossing calculation strip: base fog + cycle modifier + active wraiths + soldier conflict - passenger protection - memory protection, minimum zero. Show both final fog and light remaining before commitment. Include the exact-zero-survives reminder. A facilitator may assist during the first workshop, but the rule should not require a hidden calculation or an app.

At delivery, select everyone disembarking before awarding memories. Together-delivered linked partners earn the appropriate Joined cards; unused alternatives stay outside the active memory deck. Source identity and delivery destination still need a clear physical recording method. Use identical opaque backs so memory identity cannot be inferred while drawing.

Make the no-return-with-passengers rule visible on the return route. Review the draft's final-destination delivery safeguard on paper as well as digitally, so the player cannot unknowingly enter a state with no legal way home.

### Plan for endless play without endless setup

Repeated cohorts require fresh identities and enough soul/memory components. Provide continuation sheets or write-in fields rather than treating the printed supply as a game limit. Preserve the no-permanent-memory-removal rule; do not reuse delivered souls within a run just because cards run out.

The growing memory deck, multiple cohorts, per-soul anger and temporary markers may still make paper play demanding despite the resource cuts. Record those burdens during rehearsal before proposing further simplification. Do not silently remove abilities the user chose to keep.

A workshop can stop at an agreed time and record a paused run rather than inventing a victory condition. A photo plus a brief state sheet could support resuming: light, location, phase, cycle, visited stops, soul states, piles and used event flags. Check that reset clears run state without mixing reserve cards into the active deck.

### Validate physical usability separately

Before final printing, rehearse with rough cards and ordinary tokens. Have a new player follow the step aids while an observer records rule lookups, missed steps, arithmetic corrections, unclear markers, setup/reset effort and growing table space. Record actual observations rather than assuming fewer screens made the rules easier.

Compare the same worked examples in browser and paper: a linked delivery, soldier conflict canceled by Accord, a protected but separated waiting soul, exact-zero survival, wraith release, final-destination delivery, and a return/refill. Check rule outcomes and phase order; physical shuffling need not reproduce the browser's seeded card order.

Later print checks must cover actual-size legibility, grayscale distinctions, opaque backs, cutting, writable/erasable fields and reach across the table. Keep facilitation time and player decision time separate when recording observations.

The v0.3 workshop kit is a layout/component reference only. It contains removed resources and old rewards. Label future components v0.4 and produce matching references, rules and package together after the browser flow is tried. No v0.4 paper-readiness claim is justified yet.
